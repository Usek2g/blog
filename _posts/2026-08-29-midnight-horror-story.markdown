# リスク

前提として、Claudeをはじめとしたエージェント型AIはたしかに指定したフォルダ配下のファイルのみを閲覧・編集できるよう権限が制限されていますが、その中で実行できるコマンドはすべて実行できます。viコマンドやシェルの起動はAI自体がインストールされた言語を使ってプログラムを作成、実行するので当然利用できるですが、aws cliがインストールされていれば当然実行できます。恐ろしいのは先ほど説明したterraformと組み合わせれば、悪意あるAIがterraform destroy(作成したインフラリソースを削除する)コマンドを実行することすら可能なのです。これは決してファンタジーの話ではなく、現実で起きていることです。僕も一歩間違えれば、だった可能性があります。

さらに調べたところ、根本の原因は~/.aws/configに記載されていた[default]設定でした。
僕が普段AWS CLIを利用する際には、[ai-readonly]など権限を絞ったプロファイルを引数に与えて利用します。AIを使う際も同様です。
そもそも現在は~/.aws/credentialsにアクセスキーを直接記載することはセキュリティ的に非推奨です。昨年このブログでも以下の機能を紹介していました。

# [AWS CLIの 新機能 aws login コマンドを試してみた](https://dev.classmethod.jp/articles/aws-cli-aws-login/)

>ローカルPCからAWSを操作する場合、IAMユーザのアクセスキーをローカルに格納して利用する方法が一般的でしたが、これはアクセスキーが漏洩するセキュリティリスクから定期的にローテーションすることが求められる一方でローテーションが面倒だというジレンマがありました。それを解消する新機能がリリースされた

しかし[default]についてはずっと昔にアクセスキーを設定していたままでした。そして、**aws cliコマンドはプロファイルを省略した場合、[default]に指定されたプロファイルを利用して処理を実行します。**

# 対策

1. defaultを設定しない（推奨）
aws cliのdefaultは便利ですが、作業対象のAWSアカウント、権限別にプロファイルは分けるべきです。したがってdefaultを~/.aws/configからは削除するべきです。そうすればエージェント型AIは~/.aws/configは読むことができないため、デフォルトの[default]以外を利用することはありません。

2. permissionsを設定する（検討）
https://code.claude.com/docs/ja/permissions
settings.jsonに設定を記述することでclaude codeによる操作を拒否したり、実行する際に事前に人間に許可を求めたりすることができます。今回でいえばawsコマンドを事前にdenyとして記載しておけばclaude codeは勝手にインフラにアクセスすることはありませんでした。

ただしこのpermissionsは利便性とのトレードオフです。AIを利用している場合は、指示を出したら後は勝手に作業を進めておいてほしいことが多いです。安全に利用すれば強力なコマンドを制限することは、AIのパワーを抑制していることになります。askによる人間の承認を必要とする設定も、AIに作業を自動化していたつもりが、自分に対する承認で止まっていた、ということが起こり非効率になります。

# automodeについて

AutoMode（審査付き自動モード）はユーザのオプションに関係なくclaudeの内部で動作して、claudeが安全と判断した作業は承認を得ずに進める一方、危険と判断した場合は止めてくれるモードです。8/14からデフォルトで有効となりました。もともとはユーザのオプトインの機能だったのですが、Antropicの調査の結果「人間は内容をしっかり読まず”実行してOK、あとは聞かなくてよいよ”、を選んでしまう。それならAutoModeでAIが機械的に判断したほうが安全」という身もふたもない（でも誰だってそうする、俺だってそうする）結論に達したため、デフォルトでオンになった機能です。
そのため現在のclaudeは「指示の達成のためにできる処理は遠慮なく実行する一方、本当に危ない処理はとどまってくれる（ただし根拠はAI）」というAnthropicのお墨付きのもと動いています。今回僕が思ってもいなかったaws cliの利用ですが、叩いたAPIは読み取りAPIのみでした。破壊的なAPIを実行する際には事前に承認を求めたと思われます。
